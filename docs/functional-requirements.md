# Design Overview &amp; Functional Requirements

This page synthesizes the answers gathered in the [Hyperspectral Image Planning Document](https://leaf2qr.atlassian.net/wiki/spaces/L/pages/16416770) and [Client meeting #8 (7/08)](https://leaf2qr.atlassian.net/wiki/spaces/L/pages/16580683) into a single design overview with testable functional requirements, cross-referenced against `main` at `8680022` (2 October 2026). Where the planning document's Phase 3/4 checklists were left blank, this page proposes concrete design decisions rather than leaving them open. See the "Residual Open Questions" section for the short list of items that genuinely still require client input.

## 1. Purpose & Problem Statement

The Hyperspectral Image Inspector is built for Australian Plant Phenomics Network (APPN) facility operators, researchers, and technicians who capture hyperspectral images of plants on a routine (weekly/yearly) basis and need to derive plant-health indicators, for example nitrogen content and other biological markers of disease, from those captures.

The manufacturer's existing tool only performs basic RGB visualization and operating-the-machine functions; it does not compute vegetation indices, and the previous internal attempt at a replacement was unreliable (frequent crashes, especially during super-resolution) and had an unprofessional interface. This project replaces both with a purpose-built, reliable inspection tool.

## 2. System Overview

Data flow: a `.bil` data file plus its `.hdr` header (native ENVI, or PSI-proprietary, auto-converted to ENVI on load) is opened into a single shared `HSIData` state object. From there, the user invokes one of the following functional areas against that shared state:

- Visualization (RGB + vegetation indices + hypercube view)
- Cropping
- Calibration (dark + reference frame correction)
- Segmentation / Classification (unsupervised and supervised)
- Super Resolution (spectral-aware upscaling)

Each of the four tabs owns a reusable `HSIViewer` instance. Once Super-Resolution has produced a temporary processed `HSIData` result, its low/high-resolution control and a shared canvas switch on every other tab select the active dataset consistently. SR runs only on the uncalibrated source; starting it after calibration requires confirmation to revert calibration and its classification results. Calibration always processes the raw low-resolution source and, when available, the raw SR cube in sequence, retaining a calibrated result for each resolution rather than discarding SR. The selected resolution uses its calibrated cube when available, otherwise its raw cube. The viewer supports pan/zoom, point markers, a per-pixel value overlay, spectrum requests, and rectangular or polygon crop requests. A polygon crop keeps a rectangular spectral cube plus a boolean region-of-interest (ROI) mask; excluded pixels render transparently. Pan/zoom is mapped between resolutions to keep the same image region in view, and transferred between 2D tabs with coordinate scaling when resolutions differ. Dimension-changing crops refit the image, and crop undo/redo is connected at the main-window level.

The current UI is a 4-tab `QTabWidget` (Visualization / Super-Resolution / Calibration / Classification). Visualization switches between its 2D viewer and a dedicated PyQt6/OpenGL Hypercube widget. Classification adds a collapsible class-layer inspector beside its viewer. Hypercube preparation, calibration, SR inference/preview rendering, and both classification paths have background workers; source import and eager 2D visualization computation remain synchronous. Rectangle and polygon crop tools are available from the 2D viewers' context menus, but cropping is blocked during cube-processing workers and whenever the processed SR dataset is selected. `docs/architecture.md` describes an earlier sidebar/panel-swap design that was superseded by this tab-based layout. Treat that part of the architecture document as historical.

## 3. Functional Requirements

Requirements are written as Given/When/Then acceptance criteria, per the format the planning document itself prescribes. Status reflects implementation and wiring found on the audited `main` revision:

- **Done** — the user-facing path is implemented and connected.
- **Partial** — only part of the acceptance criterion or only some architectural layers exist.
- **UI only / Model only** — the named layer exists but there is no end-to-end workflow.
- **Not started** — no material implementation was found.

A headless `pytest`/`pytest-qt` suite is tracked in `ui_tests/` and runs in GitHub Actions on pushes to `main`, pull requests, and manual dispatches. It covers synthetic-cube import, visualization switching, rectangle and polygon crop/undo/redo/refitting, ROI-aware index values and RGB stretch, transparent polygon export, context-menu wiring, pan/zoom transfer, Hypercube geometry/controller/worker behavior, calibration discovery/numerics/crop alignment and low/high-resolution orchestration, SR lifecycle/inference contracts, K-means worker integration, polygon-ROI handling in both supervised classifiers, classification layer controls and per-class visualization means, and independent low/high-resolution classification state. Real-capture tests require locally supplied sample files. SR Model tests require optional PyTorch/SciPy dependencies, and the `sr_model` tests additionally use the tracked checkpoint to run real inference and check Qt responsiveness. CI installs only `requirements-dev.txt`, so optional SR dependency tests and real-capture tests skip there. Supervised accuracy on real captures, the full classification index-analysis API, and the new classification background selector do not yet have dedicated tracked regression tests. Headless checks do not establish desktop OpenGL-driver or packaged-build compatibility. A **Done** status records code-level implementation and any stated regression coverage, not completed stakeholder validation or scientific-accuracy validation.

Additional implemented inspection aids (not new MVP acceptance criteria): Show Pixel Values displays numeric readings with swatches from each mode's displayed color; Classification also reports the class ID, while the SR viewer supplies only RGB for its selected dataset. Index Mean opens a non-modal dialog showing the active visualization result's global mean, observed min/max, and colormap gauge. After a polygon crop, index values outside the ROI are `NaN`, so the reported mean excludes them; this is still a global mean over the retained ROI rather than per-class statistics. The action is blocked only when invoked directly from the SR viewer while Processed is selected, but remains available from Visualization for the processed index result.

### 3.3 Cropping

| Requirement | Status |
| --- | --- |
| Given a loaded cube and a user-drawn or specified rectangular region, when the user confirms the crop, then a new cube containing only that region's data (all bands) is produced. | Done: context-menu Crop applies a dragged rectangle on mouse release, retains all bands in a lazy sub-image, recomputes source displays/Hypercube, and supports undo/redo. Polygon crop also stores an ROI mask within its bounding box. Source crop/undo/redo invalidates old SR and classification results and rebuilds completed calibration; crop is blocked while calibration, SR, or classification runs and whenever the processed SR dataset is selected. UI tests cover drag signaling, recomputation, refitting, history, degenerate selections, and crop-to-export dimensions. |
| Given a loaded cube, when the user chooses Crop to Polygon and marks at least three vertices, then only pixels inside the polygon are retained for display and ROI-aware analysis, and the crop can be undone or redone. | Done: click to add vertices; double-click, right-click, or Enter to apply; Backspace removes the last vertex and Esc cancels. The spectral cube is cropped to the polygon's bounding box and stores a boolean ROI mask, not a physically non-rectangular cube. Successive polygon crops intersect their masks. Display is transparent outside the ROI; index values, index means, RGB stretch, and K-means clustering exclude those pixels. Both supervised classifiers classify only ROI pixels, leaving excluded target pixels unlabeled. Undo/redo restores the ROI until a completed calibration or SR operation clears history, and existing crop guards and downstream invalidation apply. Synthetic-cube tests cover these paths. |

### 3.4 Calibration

| Requirement | Status |
| --- | --- |
| Given a raw cube and two calibration frames, when the user selects Calibrate, then a radiometrically calibrated cube is produced and rendered. | Done: loading a timestamped source scans its folder for complete `_calibFrame` pairs captured earlier and no more than 60 seconds apart, selecting the closest pair while retaining manual overrides. Timestamped frames are ordered earlier=dark and later=bright; legacy names retain explicit selection order. `CalibrationService` averages exactly the middle 21 rows per detector column/band, broadcasts to the source's original pre-crop row count, applies the cumulative crop, and validates geometry, wavelengths, finite data, and positive bright/dark response. It streams `(raw-dark)/(bright-dark)` to a temporary float32 ENVI cube without clipping or overwriting inputs and retains the polygon ROI. A cancellable background worker reports progress, renders calibrated RGB, and surfaces actionable errors. If raw SR output exists, the same operation calibrates both resolutions sequentially, interpolating the cropped detector profiles onto 2× pixel centres for the high-resolution cube. The selected resolution's calibrated result supplies views, spectra, indices, and later classification; SR itself always reads raw data. Calibration rebuilds after a source crop and clears crop undo/redo and classification results on completion. Synthetic Model/UI tests cover discovery, numerical output, central-row selection, ROI/crop alignment, validation, worker lifecycle, cancellation, export, and SR/calibration ordering and interpolation. |

### 3.5 Segmentation / Classification

| Requirement | Status |
| --- | --- |
| Given a loaded cube, a target number of classes, and a max-iterations value, when the user runs unsupervised classification, then the image is grouped into that many spectrally-similar segments and rendered as a labeled mask. | Done: `ClassificationService` runs SPy's K-means in a Controller-owned worker and returns an HxW class map plus class-first KxHxW one-hot masks. The Classification tab validates its inputs, reports progress, supports cancellation, warns about large memory estimates, and renders a colored label overlay. It classifies the selected Original/Processed dataset and keeps each resolution's result independent. A polygon crop sends only selected pixels into clustering; excluded pixels remain unlabeled and transparent. Synthetic-cube tests exercise the worker and resolution-aware workflow. |
| Given a loaded cube, a ground-truth file, and a chosen classifier (Gaussian / Mahalanobis Distance / Perceptron), when the user runs supervised classification, then each pixel is labeled according to the trained classifier. | Partial: selecting a reference mask automatically resolves and displays its paired hyperspectral cube when available; the separate cube picker permits manual override or recovery when no pair is found. The GUI classifier selector is populated from the Model's supported enum. Its readable Gaussian and Mahalanobis distance choices run in a worker and return HxW labels plus KxHxW one-hot masks. A polygon crop classifies only selected target pixels, leaving excluded pixels unlabeled and transparent. Pairing, mask dimensions, wavelengths, and sample counts are validated with user-facing errors. Perceptron is deliberately omitted pending an agreed dimensionality-reduction/training policy. |
| Given a classification result, when the user shows, hides, solos, or renames a class layer, then the RGB/index display reflects the selected classes without changing analytical masks. | Partial: the Model supports all four operations without mutating analytical masks. The collapsible layer inspector exposes per-class show/hide and opacity, show/hide all, overall opacity, and filled/borders-only rendering. Its Visualization selector chooses RGB or an available cached vegetation index beneath the class overlay, independently of the Visualization tab's selected mode. Layer settings are retained independently for low/high-resolution results; the background choice is shared. Solo and rename exist in the Model but are not exposed in the UI. Layer-panel, compositing, debounce, and resolution-swap behavior have automated coverage; the background selector lacks dedicated regression coverage. |
| Given a classification result and vegetation-index choice, when analysis runs, then each class has its own masked raster and finite-pixel summary statistics. | Partial: class rows now show means and matching colour swatches for cached RGB and available NDVI, EVI, MCARI, MTVI, OSAVI, and PRI results. RGB means average displayed colour channels; index means use finite analytical values within each class, omit classes with no finite values, and are independent of display visibility/opacity. Means are computed on the GUI thread and invalidated when visualization results change, with Model/Controller/panel tests. The full Model analysis API also provides median, standard deviation, minimum, maximum, counts, transparent display layers, and lazy masked rasters, but that richer API still lacks a worker/UI workflow and export. |
| Given the Segmentation panel is active, when the user Ctrl+clicks to place foreground/background points or Ctrl+drags a box, then those prompts feed the selected classifier as interactive input. | Partial: Ctrl+left/right-click draws foreground/background point markers in the viewer, but implemented batch classifiers do not consume them. Box prompts and prompt undo/redo are not implemented; crop undo/redo is a separate main-window workflow. |

### 3.6 Super Resolution

| Requirement | Status |
| --- | --- |
| Given a loaded cube, when the user selects a target resolution and runs Super Resolution, then an ML-accelerated algorithm upscales the image using all spectral bands (not just RGB), with progress shown via a progress bar. | Partial: Run now performs real MSDformer inference on a background QThread using the tracked checkpoint, with progress, cancellation, error recovery, and Original/Processed RGB comparison. The current model requires exactly 480 bands and produces a fixed 2× spatial result; there is still no user-selectable target resolution or support for arbitrary band counts. The complete output cube retains all 480 bands/wavelengths, rather than upscaling only RGB. |

Current SR implementation boundaries (see [Super-Resolution](super-resolution.md)):

- PyTorch and SciPy are optional dependencies in `requirements-sr.txt`, imported only when needed. Missing dependencies/checkpoints and incompatible input produce actionable errors.
- Tiled inference writes float32 predictions to a temporary ENVI BIP cube, leaving the original file unchanged. The largest documented capture would require about 7 GiB for this temporary output; it is not a permanent HSI export.
- Low/High is a global data-source toggle: Visualization modes, Hypercube, spectrum/pixel lookup, Classification, and Save Image use the selected resolution's calibrated result when present, otherwise its raw cube. SR only consumes the uncalibrated source; running it after calibration requires confirmation to revert calibration and dependent classification before inference. Run SR first, then Calibrate to calibrate both resolutions without discarding the raw SR result. Loading/cropping/undoing the source invalidates old SR output and classification. Successful calibration or SR clears both classification slots and crop undo/redo history; successful SR also clears obsolete high-resolution calibration. SR cancellation or failure retains the previous successful SR result, but does not restore calibration already reverted at the user's confirmation. After a polygon crop, SR processes its rectangular bounding box and maps the ROI mask onto the 2× result for display and later ROI-aware calculations; the mask does not reduce inference work.
- Source load, crop/undo/redo, and spectrum reads are paused during SR to serialize file access. Tabs, cached modes, and pan/zoom remain interactive. Closing requests cancellation and waits asynchronously for SR completion.
- Model tests cover channel-preserving reconstruction, cropped/odd-size inputs, cancellation cleanup, invalid input/output/checkpoints, and actual-checkpoint agreement with a direct network call. The documented local CPU ROI run is not full-capture or ground-truth quality validation; fixed band count alone does not establish sensor/training compatibility, and tiled predictions may have seams.

| Requirement | Status |

## 4. Non-Functional Requirements

| Category | Target | Current state on `main` |
| --- | --- | --- |
| **Reliability** | Zero-crash tolerance on core operations (load, calibrate, visualize, classify, super-resolve). This is the direct pain point named by the client about the previous tool. All I/O and model-inference paths must catch exceptions and surface an error dialog instead of crashing. Session state auto-saves (via the JSON project file) after each significant action so a crash doesn't lose configuration. | Partial: import/spectrum/export errors are surfaced; Hypercube, calibration, SR, and classification workers report failures and handle cancellation. Calibration validates reference geometry/wavelengths/values and cleans temporary output. Classification validates parameters, training-file pairs, masks, wavelength alignment, sample counts, finite data, and SPy output; source-changing operations are blocked while it runs, and close waits asynchronously for cancellation. Synthetic ROI regression tests cover both supervised classifiers; real-capture accuracy remains unverified. SR validates checkpoints and finite tensors, cleans incomplete output, preserves prior successful results, and avoids destroying an active thread on close. Session auto-save remains unimplemented. |
| **Performance** | Based on the largest real capture on hand (~900 MB, 480 bands, 1971×500 px, VNIR 352–899 nm, 12-bit): long-running operations (load, super-resolution, classification) run off the UI thread with progress feedback. Target: single-tray load completes in under 10 seconds on typical facility hardware. | Partial: Hypercube preparation, calibration, SR inference/RGB preview, and classification run in background workers with progress. Calibration and SR use bounded line/tile working memory, while K-means estimates its in-memory working set and warns at 1 GB. Import, eager RGB/index rendering, and per-class visualization means still run on the GUI thread; waiting for a Hypercube reader to stop can also block it. Full-capture calibration/classification/SR runs, per-class mean latency, and the under-10-second import target remain unverified. |
| **GPU Support** | Super-resolution should auto-detect CUDA and use it when available, with mandatory CPU fallback (no assumption that deployment hardware has a GPU). | Partial validation: the optional PyTorch service selects CUDA when available and CPU otherwise; actual-checkpoint CPU tests exist. `requirements-sr.txt` now defaults to CPU PyTorch wheels, so CUDA deployment requires a suitable CUDA-enabled installation rather than that default build. CUDA execution has not been validated in the tracked local verification or CI. MPS is not enabled. |
| **Accuracy** | Vegetation indices (NDVI, EVI, MCARI, MTVI, OSAVI, PRI) follow standard published formulas; validated via unit tests against hand-calculated reference values on the sample data already in the repository, within 1% numeric tolerance. | Partial: all six formulas and wavelength-tolerance checks are implemented, and UI tests confirm that each mode renders, but no tracked reference dataset or numerical accuracy tests establish the 1% tolerance. Index results can currently be computed from uncalibrated raw data. |
| **Usability** | Target user is a skilled technical operator, not a programmer. No onboarding flow is required, but every disabled control must show a tooltip explaining why. Keyboard shortcuts and multi-monitor polish are nice-to-haves. | Partial: Calibration explains missing prerequisites, offers Run/Cancel and status progress, and identifies invalid reference data. Hypercube has interactive camera/reset/export controls; SR offers Run/Cancel and progress, with a shared low/high-resolution canvas switch on the other tabs. Classification provides readable classifier choices, working actions, progress/cancellation, deterministic colours, and a collapsible layer inspector with visibility/opacity/global/border controls, an RGB/index background selector, and per-class means with swatches. Rectangle and polygon tools are available from the viewer menu, with a polygon preview and editable vertices. Crop refits after resizing, resolution changes preserve the same 2D field of view, pixel overlays include colour swatches/class IDs, and global index means remain visible in a dialog. Disabled-control explanations are not yet consistent everywhere, and layer solo/rename are not exposed. |
| **Compatibility** | Primary target OS is Windows (typical facility workstation), with Linux supported for development. macOS is explicitly out of scope unless requested later. | Partial: `scripts/build_pyinstaller.py` and `requirements-build.txt` provide an onedir distribution with UI assets, the tracked SR checkpoint, and optional SR dependencies; it builds in a fresh venv and emits a Windows ZIP or Linux tar.xz and must run on each target OS, not cross-compile. Linux runtime compatibility depends on the builder's glibc version. Headless Ubuntu CI exercises core/UI behavior, while Hypercube requires a working OpenGL context and driver. Packaged launch/SR/OpenGL behavior and Windows acceptance remain unverified by tracked automated checks; there is no Windows CI job. |

## 5. Phase 2 Backlog (Explicitly Deferred, Not Dropped)

The six models above (Visualization, Cropping, Calibration, Segmentation/Classification, Super-Resolution, plus the Hypercube view) are the mandatory MVP scope, per the client's explicit description in meeting #8. The following were only mentioned in the earlier brainstorming stage and are deferred rather than committed to:

- PCA analysis
- Spectral unmixing
- Target detection
- General material identification
- Automated report generation

## 6. Residual Open Questions

The following items still require client input:

- Exact sensor/camera make & model. Headers already self-describe band count and wavelengths, so this is documentation-only and not blocking.
- Availability of a labeled ground-truth dataset to validate supervised-classification accuracy against.
- Whether deployment machines have GPU hardware. This doesn't block development since CPU fallback is mandatory regardless, but it affects whether GPU acceleration is ever exercised in practice.
